# IDD-0004.spec-semantic-decision-safety-and-observability

## Intent

Use local, comparatively small models only for narrow semantic judgments while
keeping book state, validation, retries, and output under application control.

## Related Specifications

- IDD-0001
- IDD-0002
- IDD-0003

## Behavior

- Each semantic operation has one narrow purpose and a small typed result. The
  product uses separate operations for TOC detection, TOC parsing, ambiguous
  heading matching, window heading classification, ambiguous noise
  classification, and review of validated anomalies.
- Semantic output contains only the decisions unavailable to deterministic code,
  such as a selected pointer and heading level; ordinary pointers remain body by
  default.
- Window heading classification labels eligible paragraphs with compact local
  numbers and returns only a minimal mapping from those numbers to heading
  levels 1 through 3. The application maps local numbers back to stable pointer
  identifiers. The model does not return body
  classifications, annotation objects, decision kinds, reasons, deferrals, or
  rewritten text. An omitted pointer remains body by default.
- Semantic input is limited to the smallest useful local context and explicitly
  identifies eligible pointer regions. Window heading classification exposes
  local numbers only for paragraphs the model may select; stable pointer
  identifiers, ordinary previous context, and look-ahead are not included. The
  input also includes the current heading level plus the levels of active
  ancestor headings. A result may select only exposed local numbers.
- Typed results are validated before use. Invalid output receives a local retry
  with the specific failure reason; it does not restart the whole workflow.
- Profiles support embedded JSON Schema, structured output when the provider
  supports it, and temperature configuration. Provider JSON mode is an aid, not
  a substitute for application validation.
- Diagnostics record each semantic call's operation, workflow step, model and
  profile, supplied pointer and candidate IDs, typed result, validation failure,
  retry count, and elapsed time. Raw prompts and responses may be retained only
  in debug mode. Diagnostics are not domain output.
- Project data separates source, domain state, workflow state, diagnostics, and
  final Markdown output.

## Product-Significant Architecture And Constraints

The product is a streaming structural parser that uses models for local
decisions; models neither rewrite a book nor generate its Markdown export.

## Non-goals

- Giving a model the full book as required context.
- Using a model's self-reported numeric confidence as an objective probability.
- Recovering malformed model JSON with a hand-written general parsing scheme.

## Acceptance Criteria

- Invalid structured output triggers a retry of only the affected semantic
  operation.
- A model cannot annotate a pointer from previous context or look-ahead.
- Stable, previous-context, look-ahead, and ancestor pointer identifiers are
  absent from the window-heading model input.
- A valid empty heading result requires no per-pointer body decisions, and a
  valid non-empty result contains only supplied eligible pointer identifiers and
  levels 1 through 3.
- The main workflow supports local models in the gpt-oss:20b class.

## Verification

- Verify empty and non-empty pointer-to-level results, malformed output, invalid
  IDs or levels, read-only pointer selection, and diagnostics for retries and
  validation failures.
